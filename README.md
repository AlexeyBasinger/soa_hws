## Ответы на вопросы
### домены и их ответственность
#### Пользователи
- Храним профили, роли (покупатель/продавец/админ), настройки.
- Отвечаем за данные пользователя. Аутинтификация через внешний сервис
- Реализуем управление ролями(покупатель/продавец/админ)
#### Каталог
- Товары, категории, цены, остатки
- Продавец управляет карточками
- Это источник истины по товарам
#### Персонализация
- Формирует персональную ленту для покупателя
- Собирает сигналы(клики, просмотры, покупки)
- Отдает список товаров в нужном порядке
#### Заказы
- Создание заказа, позиции, статусы
- Хранит жизненный цикл заказа
#### Платежи
- Инициирует платёж, хранит статусы.
- Работает с внешней платёжной системой
#### Доставка
- Создаёт доставку, хранит статусы.
- Работает с внешней службой доставки
#### Уведомления
- Отправляет письма/SMS/push по событиям.
- Подписывается на события заказов, платежей и доставки
### распределение доменов по сервисам
Каждый домен это отдельный сервис со своей бд!
- User Service - домен Пользователи(профили, роли, настройки)
- Catalog Service - домен Каталог
- Feed/Recommendation Service - домен Персонализация
- Order Service - домен Заказы(заказы, позиции, статусы)
- Payment Service - домен Платежи(платежи, статусы, интеграция с платежной системой)
- Delivery Service - домен Доставка(доставки, статусы, интеграция со службой доставки)
- Notification Service - домен Уведомления


Backend API - просто точка входа. Он проверяет токен и маршрутизирует запросы. данными не владеет!

Разделили так потому, что 
- Каждый сервис отвечает за одну понятную область и проще развивается
- У каждого сервиса своя бд -> нет общей базы и нет скрытых зависимостей.
- Интеграции с внешними системами(платежи/доставка/уведомления) вынесены отдельно
### границы владения данными
User Service/User DB: users, roles, profiles, settings, status - хранит и меняет данные пользователей

Catalog Service/Catalog DB: products, categories, attributes, price, stock, publish_status - источник истины по товарам

Feed Service/Feed DB: user_signals(views/clicks), rankings/feed_cache - формирует персональную ленту

Order Service/Order DB: orders, order_items, order_status - оформление и жизненный цикл заказа

Payment Service/Payment DB: payments, payment_status, provider_refs - платежи и их статусы, интеграция с paymentProvider

Delivery Service/Delivery DB: deliveries, delivery_status, tracking_refs - доставки и их статусы, интеграция с deliveryProvider

Notification Service/Notification DB: templates, notification_log - отправка уведомлений и журнал


Синхронные взаимодействия(HTTP):
Web/Mobile/Admin Apps - Backend API(HTTPS/JSON)
Backend API - User/Catalog/Feed/Order/Payment/Delivery/Notification(HTTP/JSON)
Payment Service - Payment Provider(API) + входящие вебхуки
Delivery Service - Delivery Provider(API) + входящие вебхуки
Notification Service - Notification Provider(API)

Асинхронные взаимодействия (Event Bus):
Order Service - Event Bus (события заказа: создан/статус изменён)
Payment Service - Event Bus (статус платежа)
Delivery Service - Event Bus (статус доставки)
Backend API - Event Bus (события поведения: просмотры/клики — для персонализации)
Feed Service <- Event Bus (подписка на поведение + события заказа/платежа для обновления ленты)
Notification Service <- Event Bus (подписка на события заказа/платежа/доставки для отправки уведомлений)
### Альтернативные варианты декомпозиции
как нам и говорили на лекции, все можно завернуть в монолит. Или же реализовать микросервисы, как у нас. Есть еще модульный монолит, но он еще хуже чем обычный
### Trade-off’ы вариантов
Плюсы и минусы понятны, неоднакратно обсуждали на лекции
#### Монолит
##### плюсы
- проще старт: один репозиторий, один деплой
- проще дебажить: всё в одном месте
- меньше инфраструктуры (без брокера, без сетевых вызовов между сервисами)
##### минусы
- общая бд
- любые изменения затрагивают весь сервис - выше риск все сломать или уронить прод целикмо
- тяжело масштабировать по нагрузке: например, лента/каталог обычно читаются намного чаще заказов
- интеграции (платёжка/доставка/уведомления) смешиваются с основным кодом, из-за этого сложнее ретраи, вебхуки, устойчивость
### Обоснование финального выбора
Тут уже и не знаю, что сказать, после прочитанного выше все очевидно. Монолит на практике используется для легких проектов, да и то не всегда! Так как у него крайне тяделые минусы. Все неаккуратно и в одном месте, куча зависимостей. Вышеперечисленное тянет за собой проблемы с реализацией и дальнейшей поддержкой платформы. 
Так как маркетплейс все таки большой проект и мы нацелены, что он проживет дольше двух недель, то конечно выбираем микросервисы
